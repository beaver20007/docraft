# H8 — Source of truth для CI: факты и рекомендация

**Дата:** 2026-09-03 (сессия-4, ночной прогон)
**Статус:** ⏳ **решение за владельцем.** Здесь только факты и рекомендация с обоснованием —
архитектурное решение Оркестратор не принимает (стоп-правило протокола).

---

## Вопрос (из аудита, п. 8)

CI в docraft чекаутит внешний репозиторий `beaver20007/ai-playbook-generator`, а не
submodule `apps/ai-playbook` внутри docraft. Какой репозиторий — source of truth?
Синхронизированы ли они?

---

## Факты

### 1. Репозитории сейчас синхронны — байт-в-байт один коммит

```
gh api repos/beaver20007/ai-playbook-generator/commits/main --jq .sha
→ 80c0418cacaeddd996fe0e0f64f8ded66ea90fcd

git ls-tree origin/main apps/ai-playbook
→ 160000 commit 80c0418cacaeddd996fe0e0f64f8ded66ea90fcd  apps/ai-playbook
```

Расхождения нет **на данный момент**. Но синхронность держится только дисциплиной
Оркестратора (правило 11 — обновлять указатель submodule отдельным коммитом), механической
гарантии нет.

### 2. Workflow тестирует не то, что его запустило — логическая дыра

`.github/workflows/ai-playbook-ci.yml`:

```yaml
on:
  pull_request:
    paths:
      - "apps/ai-playbook/**"     # ← триггер: изменения submodule В DOCRAFT
...
      - uses: actions/checkout@v4
        with:
          repository: beaver20007/ai-playbook-generator   # ← а чекаутит ВНЕШНИЙ репо
          token: ${{ secrets.GH_PAT || secrets.GITHUB_TOKEN }}
          path: .
```

Ветка внешнего репо не указана → берётся его **default branch**. То есть PR в docraft,
двигающий указатель submodule на коммит X, прогонит тесты против `main` внешнего репо —
**не против X**. Зелёный прогон здесь ничего не говорит о содержимом PR. Это не «настройка
под вкус», а несоответствие триггера и предмета проверки.

### 3. Дублирование: у внешнего репо есть свой CI

`apps/ai-playbook/.github/workflows/ci.yml` — собственный pytest-прогон репозитория
`ai-playbook-generator` на его push/PR. То есть один и тот же код потенциально проверяется
дважды, из двух мест, с разными правами доступа.

### 4. CI фактически не используется — политика владельца

Раздел 10 ORCHESTRATOR.md (решение владельца 2026-07-21): облачный GitHub Actions не
используем, биллинг не чиним, красный статус ожидаем и ничего не значит; единственный
валидный сигнал — локальный прогон.

Подтверждается историей: последний прогон `ai-playbook CI` — **2026-06-29**, два месяца
назад; единственный success за пятёрку последних — ручной `workflow_dispatch`.

```
completed  success  ai-playbook CI  main  workflow_dispatch  2026-06-29T11:24:08Z
completed  failure  ai-playbook CI  main  push               2026-06-29T11:04:42Z
completed  failure  ai-playbook CI  ...   pull_request       2026-06-29T10:57:24Z
```

### 5. Секрет `GH_PAT` — остаточная поверхность риска

Workflow рассчитывает на `GH_PAT` (внешний репо приватный, `GITHUB_TOKEN` до него не
достаёт). Это тот же класс секрета, что уже давал инцидент (раздел 11 ORCHESTRATOR.md:
PAT в открытом виде в `.git/config`, ротирован). Неиспользуемый workflow, требующий живого
PAT, — это хранимый секрет без выгоды.

### 6. Практический асимметричный факт (найден в эту сессию)

- remote суперрепо docraft — **SSH** (`git@github.com:beaver20007/docraft.git`), пуш работает;
- remote submodule ai-playbook — **HTTPS**, пуш с этой машины **не работает**: credential
  helper падает (`C:/Program: No such file or directory` — известный fork-баг Git for Windows,
  зафиксирован в глобальном CLAUDE.md).

Это не про CI напрямую, но влияет на выбор: сценарий «работать преимущественно во внешнем
репо» сегодня технически затруднён с этой машины, пока remote не переведён на SSH (менять
remote самостоятельно запрещено правилом — это решение владельца).

## Варианты (с ценой каждого)

### Вариант A — source of truth = внешний репо, CI живёт только там

docraft остаётся тонким суперрепо-указателем; `ai-playbook-ci.yml` из docraft **удаляется**
(его работу делает `ci.yml` внутри ai-playbook-generator).

- ➕ убирает дыру п.2 целиком: проверяется ровно тот код, что менялся;
- ➕ убирает нужду в `GH_PAT` на стороне docraft (п.5);
- ➖ docraft перестаёт иметь собственный сигнал качества по submodule;
- ➖ требует перевести remote submodule на SSH, иначе с этой машины туда не пушится (п.6).

### Вариант B — source of truth = docraft, CI чекаутит submodule

Workflow переписывается на `actions/checkout` с `submodules: recursive` самого docraft,
внешний репо становится зеркалом.

- ➕ проверяется именно то состояние, которое лежит в PR docraft;
- ➕ монорепо-дисциплина: один PR = одно состояние всего продукта;
- ➖ внешний репо всё равно нужен (Railway деплоит из него — проверить перед решением!);
- ➖ дублирующий `ci.yml` внутри submodule надо отключать, иначе двойной прогон.

### Вариант C — удалить `ai-playbook-ci.yml`, ничего не заменять

Честно зафиксировать: облачный CI не используется по решению владельца (раздел 10),
качество держится локальными прогонами Оркестратора.

- ➕ убирает мёртвый workflow, вводящий в заблуждение красным статусом;
- ➕ снимает потребность в `GH_PAT`;
- ➖ если политика когда-нибудь изменится, придётся заводить заново;
- ➖ остаётся `ci.yml` внутри submodule (тоже фактически не используемый).

---

## Рекомендация Оркестратора

**Вариант C сейчас, вариант A как целевой — если/когда CI понадобится.**

Обоснование:

1. **Решать «какой репо главный для CI» имеет смысл только если CI используется.** По
   действующей политике владельца он не используется два месяца, и красный статус
   сознательно игнорируется. Пока это так, выбор между A и B — оптимизация того, что не
   работает.
2. **Мёртвый workflow не нейтрален**: он даёт ложный сигнал (красный бейдж, который надо
   каждый раз объяснять новой сессии) и держит требование живого `GH_PAT` — секрета того
   же класса, что уже приводил к инциденту.
3. **Если CI понадобится — целевой вариант A, не B**, потому что реальный поток работы уже
   устроен так: код меняется через PR во внешнем репо (`ai-playbook-generator`, PR #19 →
   `80c0418`), а docraft лишь двигает указатель. CI логичнее держать там, где рождается код.
   Вариант B ломает этот поток ради монорепо-дисциплины, которой в проекте фактически нет.

**Что нужно проверить владельцу перед решением (Оркестратор не проверял — нет доступа):**
из какого репозитория Railway тянет код на деплой. Если из `ai-playbook-generator` — это
дополнительный аргумент за A/C; если из docraft — вариант B становится сильнее.
