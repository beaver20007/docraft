x0=  76.0 x1= 518.8  'curl -X POST https://api.example.com/v1/organizations/9f3b2c1a/p'

## Но предпосылка «лечится как render-002» — неверна

Прямое измерение через ReportLab (`Paragraph.wrap` на реальной ширине рамки
`455.3pt` = A4 − поля − паддинги таблицы кода):

| вариант | строк | занятая ширина по строкам |
|---|---|---|
| **текущий** (`splitLongWords=1`) | 2 | 451.0 и 176.7 — **обе внутри рамки** |
| **предлагаемый** (`splitLongWords=False`) | 1 | **627.7 при рамке 455.3** — шире на 172pt |

`splitLongWords=False` не «чинит перенос», а **отключает единственный доступный способ
уместить токен**: строка вылезает за пределы серого блока кода и уезжает к краю страницы.

**Почему в `stats_grid`/`table_renderer` то же лекарство сработало, а здесь нет.**
Там дефект был в том, что рвалось **обычное слово** (`«квалифицированных»`), которое имело
альтернативу: перенос по границе слова плюс подбор кегля по реальным метрикам, чтобы
широчайший токен влез в колонку. У кода альтернативы нет: URL или base64 — это **один
неразрывный токен**, который не помещается в строку ни при каком читаемом кегле. Посимвольный
перенос здесь не баг раскладки, а **единственный способ удержать текст внутри блока** — и
ровно та конвенция, по которой ведут себя все редакторы и подсветчики кода.

## Вывод

Трек `render-003` закрывается как **отклонённый по существу**, а не как выполненный.
Кода в `code_block.py` не менял. Если когда-нибудь захочется убрать посимвольный разрыв
по-настоящему, это другая и куда более дорогая работа: измерять ширину токена метриками,
подбирать кегль до пола читаемости, а для не влезающего и на полу — вводить явный маркер
переноса (как `↩` в редакторах) либо горизонтальную прокрутку, которой в PDF нет.
Это уже продуктовое решение об оформлении кода, а не устранение регрессии.

## 🔴 Попутная находка — кандидат `render-004`: код молча теряется

При воспроизведении обнаружилось, что `code_block.py:41` отдаёт текст кода в ReportLab
**без экранирования разметки**:

```python
code_text = block.get("code", "").replace("\n", "<br/>").replace(" ", "&nbsp;")
code_para = Paragraph(code_text, code_style)
```

`Paragraph` разбирает мини-HTML. Что это даёт на реальных сниппетах (мой прогон, тема
`premium`, текст извлечён из готового PDF):

| вход | что попало в PDF |
|---|---|
| `<div class='card'>ok</div>` | **`ok`** — теги и их содержимое **съедены** |
| `curl 'https://x.io/?a=1&signature=zz'` | `curl 'https://x.io/?a=1&signature;=zz'` — вставлен `;` |
| `if (a && b) { return a; }` | без искажений |
| `for (i = 0; i < n; i++)` | без искажений |

То есть **фрагмент кода с HTML/XML-разметкой теряется беззвучно** — не падает, не
предупреждает, просто исчезает из документа. Для продукта, который генерирует
документацию с примерами кода, это тяжелее, чем некрасивый перенос.

**Почему не починил здесь же:** фикс сам по себе однострочный
(`xml.sax.saxutils.escape()` до подстановки `<br/>`), но он **меняет наблюдаемый вывод**
на уже существующих документах — там, где сейчас код теряется, он начнёт появляться.
Это правка рендера с видимым эффектом, а такие в этом проекте делаются по явному
решению владельца, а не попутно в треке про перенос строк. Плюс правило «один файл —
один владелец»: смешивать отклонённый `render-003` и новый фикс в одном PR нельзя.

**Предлагаю завести `render-004`** с этим ТЗ: экранировать разметку в `code_block.py`,
закрепить тестом на всех четырёх кейсах выше, проверить, что `<br/>`/`&nbsp;`
по-прежнему работают как задумано. Оценка — небольшая; риск — низкий; эффект —
восстановление теряемого содержимого.
