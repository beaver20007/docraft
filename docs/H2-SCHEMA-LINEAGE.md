# H2 — `profiles` против `user_profiles`: это не опечатка, а две линии схемы

**Дата:** 2026-09-04 (сессия-5)
**Повод:** владелец перед ручным применением миграции проверил прод-БД и обнаружил, что
таблицы `user_profiles`, под которую написана миграция, **в проде нет** — есть только
`public.profiles`. Правильно, что остановился: применять было нечего и не к чему.

**Короткий ответ:** опечатки в файле миграции нет, и «две сущности по замыслу» — тоже нет.
В проекте сосуществуют **две конкурирующие линии схемы**, и прод живёт по той, по которой
код не работает.

---

## Что показали факты

### Линия A — черновик. Это то, что стоит в проде

`apps/ai-playbook/docs/supabase-schema.sql` (тот самый файл из карантина, раздел 5
ORCHESTRATOR.md). В шапке прямым текстом: `-- Run this in Supabase SQL Editor`.

```sql
create table if not exists public.profiles (
  id          uuid references auth.users(id) on delete cascade primary key,
  email       text,
  full_name   text,
  plan        text not null default 'free',  -- free | pro | team
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
```

Ключ — `id`. Есть `email`, `full_name`. План — три значения (`free | pro | team`).

### Линия B — рабочие миграции репозитория. В проде их нет

`apps/ai-playbook/supabase/migrations/20250604_user_profiles.sql` (и то же в
`supabase/schema.sql`):

```sql
create table if not exists public.user_profiles (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  plan       text not null default 'free' check (plan in ('free', 'pro')),
  updated_at timestamptz not null default now()
);
```

Ключ — `user_id`. Ни `email`, ни `full_name`. План — два значения с `check`-ограничением.
Сюда же относятся `documents` и `exports` из `supabase/schema.sql`.

### Код работает ИСКЛЮЧИТЕЛЬНО с линией B

```
billing_service.py:87   {_rest_base()}/user_profiles     ← чтение плана
billing_service.py:124  {_rest_base()}/exports           ← подсчёт квоты за месяц
stripe_service.py:25    {_rest_base()}/user_profiles     ← запись при вебхуке
stripe_service.py:39    {_rest_base()}/user_profiles
stripe_service.py:52    {_rest_base()}/user_profiles
```

Обращений к `profiles` в API **ноль** (полнотекстовый поиск по `apps/api/app`).

## Вывод

1. **Миграцию `20260612_stripe_customer_id.sql` править не нужно.** Она корректно
   привязывает `stripe_customer_id` к `user_profiles` — именно к той таблице, которую
   читает и пишет биллинг. Переписать её на `profiles` означало бы добавить колонку в
   таблицу, к которой код не обращается: биллинг как не работал, так и не заработал бы.
2. **Настоящая причина сбоя другая:** в проде **никогда не применялась предыдущая миграция**
   `20250604_user_profiles.sql`. Применять `stripe_customer_id` поверх отсутствующей таблицы
   бессмысленно — Postgres ответит `relation "public.user_profiles" does not exist`.
3. **Заодно закрыт вопрос 10 из H7** («применялся ли черновик `supabase-schema.sql`»):
   да, применялся — именно он и стоит в проде. А рабочие миграции репозитория — нет.

## Чем это оборачивается на живом проде прямо сейчас

Ничего не падает, и это худший вид поломки — **тихий**. Оба обращения к отсутствующим
таблицам сделаны fail-open:

- `fetch_user_plan` (`billing_service.py:96-105`): при любом не-200 логирует WARNING и
  возвращает `_default_plan_for_user(...)` → фактически **все пользователи всегда `free`**,
  независимо от того, платили они или нет;
- `count_exports_this_month` (`billing_service.py:134-146`): при не-200 возвращает `0` →
  **месячная квота никогда не расходуется**.

То есть биллинг на проде сейчас не «сломан с ошибкой», а **бесшумно выключен**. Для
pre-launch это терпимо (платящих нет), но включать Stripe (H1) **до** починки схемы нельзя:
вебхук напишет план в `user_profiles`, которой не существует, оплата пройдёт, а доступ не
изменится.

---

## Что делать — решение владельца

### Вариант A (рекомендуемый) — привести прод к линии B, как ждёт код

Применить в SQL Editor **по порядку**: сначала `20250604_user_profiles.sql`, затем
`20260612_stripe_customer_id.sql`. Дополнительно из `supabase/schema.sql` — `documents` и
`exports`, иначе квота продолжит считаться нулём.

- ➕ совпадает с кодом, менять код не нужно; все стейтменты идемпотентны (`if not exists`);
- ➕ ничего не удаляет: `profiles` остаётся нетронутой;
- ➖ в базе останутся две таблицы профилей — `profiles` (осиротевшая) и `user_profiles`
  (рабочая). Осиротевшую можно снести отдельным решением позже, **не в этом шаге**;
- ⚠️ **если в `profiles` есть живые данные** (реальные пользователи с проставленным
  `plan='pro'`), их надо перенести в `user_profiles` — это данные, поэтому решение и SQL
  переноса за владельцем. Оркестратор вслепую перенос не пишет.

### Вариант B — привести код к линии A (`profiles`)

Переписать пять обращений в `billing_service.py`/`stripe_service.py` на `profiles` и
поменять имя ключа `user_id` → `id`. Плюс завести `exports`/`documents` всё равно
(их в проде тоже нет).

- ➕ прод-БД не трогается вовсе;
- ➖ это уже правка кода биллинга, а не миграция; нужен трек, тесты и деплой;
- ➖ `plan` в черновике без `check`-ограничения и с третьим значением `team`, которого код
  не знает (`rows[0].get("plan") in ("free", "pro")`) — тихое расхождение контракта.

**Рекомендация Оркестратора: вариант A.** Он аддитивен, обратим и не требует ни правки кода,
ни деплоя. Решение — за владельцем; Оркестратор к прод-БД не идёт (см. H22).

## Открытый вопрос владельцу

**Есть ли в `public.profiles` живые строки, и есть ли среди них `plan` = `pro`/`team`?**
Если да — перенос данных нужен и должен быть написан явно. Если таблица пуста (вероятно,
раз биллинг никогда не работал), вариант A применяется как есть, без переноса.
